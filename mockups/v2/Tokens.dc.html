The face, embedded — not linked, not a fallback list

@font-face { font-family: "StoryAtlas Mono";
  src: url(data:font/woff2;base64,…) }

A subsetted woff2 as a data: URI satisfies “no external resource” — nothing is fetched — while keeping TextStyle.family a single named face rather than the fallback list the type deliberately forbids. ~30–60 KB per weight.

UI chrome keeps the system stack, because no receipt depends on its metrics.

Portable fallback stack — screen only

ui-monospace, SFMono-Regular,
Menlo, "DejaVu Sans Mono", monospace

No webfont, so nothing to block, and export shows the same faces the screen does. Today TextStyle.cssFamily emits one bare family and forbids a fallback list; shipping these stacks needs that to admit one.

Why the face must be pinned, not named

Pagination is computed from a fixed cell metric — MonospaceMeasurer, CellPerEm 600, so 9.6px per column at 16px. But cssFamily emits the bare keyword monospace, which resolves per platform: Menlo and DejaVu are ≈0.60 em, Consolas ≈0.55.

On a reader whose monospace is narrower, the static edition's absolutely-positioned overlays drift from the text they annotate — and no test catches it, because static.cjs checks the header numbers against the receipt, not the rendering against the numbers. The live shell escapes only because it defaults to dom-canvas/1.

Embedding makes the assumed advance true, so the receipt names a metric that actually travels with the artifact. v2 also proposes leading 1200 → 1550 per em and a 58-column measure.
